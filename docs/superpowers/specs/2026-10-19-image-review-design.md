# 카드뉴스 이미지 검토 비서

작성일: 2026-10-19 · 상태: 구현 전 설계 검토

## 해결할 문제

사용자는 GPT 프로젝트에서 카드뉴스를 만들지만, 부분 수정을 요청할 때 원하는 디자인이 유지되지 않는 데 불편을 겪었다. 현재 웹 편집기는 입력과 조작 단계가 많고 사용자의 기존 디자인도 재현하지 못한다.

사용자가 제안하고 동의한 새 중심 작업은 **완성한 이미지 여러 장을 올려 장별 검토를 받고, 수정한 장만 다시 검토하는 것**이다. 수식·개념·도식의 정확성을 먼저 보고, 디자인 일관성과 가독성도 함께 확인한다. 원본을 다시 생성하거나 편집 가능한 템플릿으로 옮기도록 요구하지 않는다.

완료 기준은 사용자가 실제 카드뉴스 1세트를 가지고 업로드 → 장별 지적 확인 → 외부에서 수정 → 해당 장 교체 → 재검토를 수행할 수 있는 것이다. 자동 검토가 정확성을 보증한다는 표현은 사용하지 않는다.

## 선택한 접근

1. **이미지 검토 중심 화면으로 전환한다.** 기존 제작 도구는 보조 메뉴로 이동한다. 사용자가 이미 만든 결과물을 그대로 검토할 수 있어 가장 적은 추가 작업이 든다.
2. 기존 편집기에 이미지 입력만 추가하는 안은 선택하지 않는다. 사용자가 지적한 복잡한 화면과 제작 경로가 그대로 남는다.
3. 이미지 자동 수정·재생성은 첫 버전에서 제외한다. 원래 디자인이 유지되지 않던 문제를 다시 만들 수 있고, 검토 품질과는 별도 검증이 필요하다.

## 화면과 사용 순서

### 1. 첫 화면: 이미지 올리기

- 큰 이미지 선택 영역과 최근 검토 목록을 보여준다. 로그인은 기존 Google 로그인을 재사용한다.
- PNG/JPEG/WebP 정지 이미지 1~10장을 한 번에 선택할 수 있다. 원본 파일은 장당 10MB까지 받는다. 실패한 파일은 이름과 원인을 표시하고, 정상 파일을 없애지 않는다.
- 썸네일과 파일명으로 순서를 보여준다. 순서는 파일명 자연 정렬을 초기값으로 하고, ‘앞으로/뒤로’ 버튼으로 바꿀 수 있다. 업로드 전 순서를 확인한다.
- 선택 사항은 ‘이번 검토에서 특히 볼 점’ 한 칸이다. 사용자가 ‘기본 검토 기준으로 저장’을 선택한 경우에만 다음 작업에 재사용한다.
- ‘전체 검토’가 유일한 주 작업 버튼이다. 장별로 범위 체크박스를 먼저 고르게 하지 않는다.

### 2. 결과: 이미지 옆에 장별 지적

- 데스크톱은 왼쪽 카드 목록, 가운데 확대 가능한 이미지, 오른쪽 검토 결과를 배치한다. 모바일은 이미지 아래에 해당 장 결과를 배치한다.
- 카드 목록에는 장 번호와 지적 개수를 표시한다. 별도 ‘전체 카드 연결 검토’ 항목에서 앞뒤 카드의 표기·설명·디자인 일관성을 본다.
- 지적은 세 종류다: `수정 필요`(이미지에서 확인되는 구체적인 모순·오류), `확인 필요`(판독 불가·조건 부족·외부 근거 필요), `표현 개선`(가독성·설명·일관성 제안).
- 각 지적에 `위치 또는 인용 → 문제 → 이유 → 수정 제안`을 표시한다. 수식 제안은 LaTeX와 읽을 수 있는 설명을 제공한다.
- 지적이 없는 장도 반드시 결과를 반환하고 ‘이번 검토에서 지적 없음’으로 표시한다. ‘정확성 검증 완료’나 ‘게시 안전’으로 표현하지 않는다.
- 읽기 어려운 글자·수식·화살표는 추정해 단정하지 않는다. 해당 부위의 확대 이미지가 필요하다고 안내한다.
- 첫 버전에서는 정밀한 이미지 좌표 강조를 약속하지 않는다. ‘상단 수식’, 인용 문구 등으로 위치를 명시한다.

### 3. 고친 장만 다시 검토

- 선택한 장에 ‘수정 이미지로 교체’ 버튼을 둔다. 다른 장의 순서와 검토 결과는 유지한다.
- 교체 직후 기존 지적을 자동 해결로 바꾸지 않고 ‘새 이미지 재검토 필요’로 표시한다.
- ‘이 장 재검토’는 새 이미지, 직전 이미지, 이전 지적과 다른 장의 맥락을 모델에 전달한다. 선택한 장의 새 결과와 이전 지적의 `해결됨 / 남아 있음 / 판단 보류`를 제안한다. 최종 확인은 사용자 체크로 따로 기록한다.
- 다른 장까지 영향을 주는 기호·설명·디자인 지적은 교체 후 ‘전체 연결 검토 갱신 필요’로 표시한다. 전체 재검토를 실행해야 갱신한다.
- 기존 지적과 이미지를 덮어쓰지 않고 해당 장의 이전 버전으로 다시 볼 수 있다. 검토 실패 시 직전 성공 결과를 유지한다.

## 저장과 개인정보 경계

- 로그인·허용 UID 검사와 모든 문서의 소유권 검사를 유지한다.
- **첫 버전의 이미지 원본·검토용 이미지·썸네일은 브라우저 IndexedDB에 저장한다.** Firestore에 이미지의 base64를 넣지 않으며, 별도 파일 저장 서비스를 새로 만들지 않는다.
- Firestore에는 검토 제목, 파일명, 이미지 해시, 장 번호·버전, 적용 검토 기준, 결과, 사용자 체크, 요청 상태를 저장한다. 컬렉션은 `image_reviews`, `image_review_versions`, `image_review_requests`로 구분한다. 큰 작업은 카드 버전별 문서로 나누어 단일 문서에 모든 결과를 누적하지 않는다.
- 화면에 ‘이미지는 이 브라우저에 보관됩니다’를 표시한다. 다른 기기 또는 브라우저 저장소 삭제 후에는 검토 문구는 불러오되 이미지가 필요하면 다시 선택하게 한다. 같은 이미지인지 해시로 확인하며 다른 파일을 과거 버전에 연결하지 않는다.
- IndexedDB 쓰기 실패·용량 초과는 검토 시작 전에 알린다. 로그인 변경 후 이전 계정의 작업과 이미지를 화면에 노출하지 않는다.
- 업로드할 때 이미지가 검토를 위해 현재 설정된 AI 제공업체로 전송된다는 설명을 표시한다. 기존 원고·대화·개인 시계열 데이터를 이미지 검토에 자동 전송하지 않는다.
- 사용자 실제 이미지·원고·검토 내용은 Git 저장소, 공개 스크린샷 또는 로그에 포함하지 않는다.

## API와 모델 처리

기존 FastAPI 앱에 독립적인 검토 라우터·서비스·Pydantic 스키마와 프론트 모듈을 추가한다. 기존 생성 모델 인터페이스와 이미지 검토 인터페이스는 분리하되, 제공업체 설정·인증·사용량 제한·저장소 패턴은 재사용한다.

- `POST /api/image-reviews`: 검토 작업 생성. 요청 UUID로 중복 생성 방지.
- `GET /api/image-reviews`: 본인의 최근 검토 목록. 전체 이미지·결과를 포함하지 않는 요약 응답.
- `GET /api/image-reviews/{id}`: 장 목록·현재 결과·검토 기준·버전 조회.
- `POST /api/image-reviews/{id}/runs`: 전체 또는 선택 장 재검토. 이미지·장 ID·해시·기준 버전·요청 UUID를 포함한다. 선택 장 교체는 이 요청에서 결과와 함께 원자적으로 새 버전으로 저장한다.
- `GET /api/image-reviews/{id}/runs/{request_id}`: 응답 지연·저장 응답 유실 후 같은 결과 복구. 다시 모델을 호출하지 않는다.
- `GET /api/image-reviews/{id}/cards/{card_id}/versions`: 장별 이전 이미지 해시·검토 결과 조회.
- `PUT /api/image-reviews/{id}/checks/{finding_id}`: 해당 지적을 사용자가 확인했는지 저장. ‘모델이 해결됐다고 제안함’과 ‘사용자 확인’을 구분한다.

브라우저는 검토용 이미지를 긴 변 2,400px 이하로 축소하고, 한 장 1MB 이하로 만든다. 해당 크기에서 읽을 수 없으면 원본 확대 확인 대상으로 남긴다. 요청 본문은 최대 16MB이며 서버에서도 제한한다. 서버는 base64 길이, 실제 디코딩 가능 여부, MIME 일치, 해상도·픽셀 수, 장 개수·소유권·중복 장 ID를 검사한다. 클라이언트가 보낸 파일명·장 번호만으로 소유권이나 이미지 일치를 신뢰하지 않는다.

전체 검토는 모든 이미지를 한 요청의 명시된 장 ID와 묶어 전달하여 장 사이 관계를 읽도록 한다. 이미지 안의 문구는 검토할 자료이지 시스템 명령이 아니다. 결과는 카드당 최대 5개, 연결 지적 최대 5개로 제한하고 근거 없는 지적을 채워 넣지 않는다. 모델 응답을 스키마로 검증하고 요청에 없는 장 ID, 빠진 장, 중복 장·지적, 알 수 없는 이전 지적 ID는 거부한다. 출력이 잘렸다면 성공으로 저장하지 않는다.

현재 코드에는 OpenAI와 Anthropic 호환 제공업체가 있다. **현재 운영 제공업체의 이미지 입력 지원은 미확인이다.** 구현 시 두 전송 형식을 각각 테스트하고, 현재 설정으로 합성 이미지의 실제 호출을 검증한다. 이미지 기능이 지원되지 않으면 명확한 설정 오류를 반환하며 텍스트만으로 검토한 척하지 않는다. 제공업체를 몰래 변경하지 않는다. 원래 과제의 GPT API 요구 충족 여부는 별도로 명시한다.

요청 예약과 일일 사용량 제한은 기존 방식을 재사용한다. 모델 호출 동안 Firestore 트랜잭션을 열지 않는다. 같은 UUID 재시도는 기존 완료 결과를 반환하고, 실행 중이면 중복 호출을 막는다. 모델 결과 저장 후 응답이 끊겨도 상태 조회로 복구한다. 기준 버전이 달라지면 충돌을 반환하여 오래된 검토가 새 이미지를 덮어쓰지 않게 한다. 브라우저에서는 1회 검토 시간과 Render 콜드스타트 로딩을 표시하고 검토 중 이탈·파일 교체로 결과가 잘못 연결되는 것을 막는다.

## 기존 기능·과제 요건과의 관계

- 새 첫 화면은 이미지 검토다. 기존 원고 편집·기획 대화는 ‘제작 도구’, 데이터·통계는 ‘계정 데이터’로 접근 가능하게 유지한다.
- 기존 Firestore 자료·시계열·대화·원고를 삭제하거나 변환하지 않는다. 기존 API 계약은 유지한다.
- 과제의 100개 이상 시계열, CRUD, 데이터 요약을 주입한 채팅, 대화 저장·불러오기, Swagger, Render·Vercel 배포 요건을 기존 기능으로 유지한다. 이미지 검토만으로 시계열 분석 요건을 충족한다고 주장하지 않는다.
- 자동 게시, 이미지 자동 수정, OCR 전용 파이프라인, 외부 근거 검색, 새 파일 저장 서비스는 첫 버전에 포함하지 않는다.

## 검증과 완료 조건

1. 합성 카드 6장으로 한 번 업로드하고 모든 장에 빠짐없는 결과가 연결되는지 확인한다. 파일명을 중복시켜도 카드 ID로 정확히 연결되어야 한다.
2. 정답을 아는 합성 예시로 수식 부호 모순·단위 불일치·도식 방향 불일치를 포함하고, 흐릿한 수식은 단정 대신 확인 필요로 나오는지 실제 설정 모델로 관찰한다. 이 소수 사례를 전체 정확도 지표로 일반화하지 않는다.
3. 한 장 교체·재검토 후 나머지 장과 결과가 유지되고 이전 버전을 다시 볼 수 있어야 한다. 기존 연결 검토는 재검토 필요 상태여야 한다.
4. 다른 UID 접근 차단, 이미지 안의 지시문 무시, 잘못된 MIME·큰 파일·손상 이미지·출력 누락·잘림·거부·중복 요청·오래된 버전·저장 응답 유실을 테스트한다.
5. 새로고침 후 동일 브라우저에서 이미지와 결과가 복구되는지, 로컬 이미지가 없으면 명확히 재선택을 안내하는지 확인한다. 브라우저 저장 실패도 테스트한다.
6. 데스크톱과 모바일에서 업로드·카드 이동·확대·지적 확인·이미지 교체를 실제 브라우저로 검증하고 합성 이미지로 스크린샷을 남긴다.
7. 기존 CRUD·요약·채팅·기록·카드 편집 회귀 테스트를 통과한다. README에 새 사용법, 로컬 이미지 보관 한계, 실제 모델 검증 범위를 기록한다.
8. 구현·검증 결과를 PR로 제시한다. 운영 반영 시 프론트·백엔드 모두 동일 변경이 반영됐는지 확인하고, 실제 사용자 자료로 무단 비용 발생 검토나 공개 업로드를 하지 않는다.

## 현재 확인 상태

- 확인됨: 현재 코드의 Firebase 소유권 검사, Firestore 트랜잭션 어댑터, 제공업체 선택, 기존 카드·채팅·시계열 기능.
- 이번에 합의함: 이미지 여러 장, 장별 검토, 수식·개념·도식 우선, 디자인·가독성 보조, 수정 이미지 재검토.
- 설계 선택으로 검토 요청: 이미지의 동일 브라우저 보관, 장수·크기 제한, 첫 화면 전환, 첫 버전 자동 수정 제외.
- 아직 구현·검증하지 않음: 이미지 입력·저장·모델 호출·검토 화면 전체.
