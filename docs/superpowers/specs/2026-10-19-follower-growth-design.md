# 팔로워 성장 비서 재구성 설계

작성일: 2026-10-19. 상태: 대화에서 방향 승인, 이 문서 검토 대기. 제품 코드는 아직 변경하지 않았다.

## 1. 목적과 완료 기준

사용자의 최우선 목표는 **팔로워 늘리기**다. Buffer에서 개인 계정의 게시 정보와 성과를 가져와 다음 게시 결정을 돕고, 추천을 참고해 올린 게시물의 결과를 기록한다. 사용자가 데이터를 매번 옮겨 적거나 여러 제작 도구를 거칠 필요가 없게 한다.

핵심 흐름은 `동기화 → 게시 형식·주제 선택 → 시간 후보와 근거 확인 → 실험 저장 → 실제 게시물 연결 → 결과 확인`이다. 성공의 첫 기준은 이 흐름이 실제 데이터로 작동하고, 모르는 성과를 모른다고 표시하는 것이다. 팔로워 증가나 추천의 인과적 효과는 제품 구현 완료만으로 입증되지 않는다.

FastAPI, Firestore, GPT API, 바닐라 HTML/CSS/JavaScript, Render, Vercel을 유지한다. 기존 데이터 CRUD·통계·대화 기록·요청 복구를 재사용한다. 다른 에이전트 프레임워크나 벡터 DB는 도입하지 않는다.

검토한 대안은 시간 추천만 제공하는 방식, 계정 운영 전체를 다루는 방식, 게시 전 추천과 게시 후 회고를 연결하는 방식이다. 현재 표본 수와 사용자의 단순한 사용 흐름을 고려해 세 번째를 선택했다.

## 2. 실제 데이터와 준비 상태

아래는 2026-10-19 로컬의 실제 Buffer 조회 결과와 CSV를 확인한 수치다. 공개 저장소에 원문·실제 성과 파일·스크린샷을 넣지 않는다.

- Buffer 전체 페이지 조회: 51개. 현재 조회 결과는 모두 게시 완료 상태다. 예약·초안이 없는 것은 이 조회 결과의 상태이며 Instagram 전체 이력이 없다는 뜻이 아니다.
- 릴스 37개, `post` 13개, 스토리 1개. 13개 `post`는 모두 복수 첨부물이며 카드형으로 구분할 수 있다.
- 캡션 50개, 첨부물 메타데이터 51개. 실제 게시 시각 `sentAt`, 예약 시각 `dueAt`, 성과 갱신 시각 `metricsUpdatedAt`을 구분할 수 있다.
- 조회·도달은 51개, 저장·공유·댓글 수는 50개에서 확인됐다. **게시물별 팔로우 수는 카드형 13개에서만 확인됐으며 릴스에는 없다.**
- 릴스에는 시청 시간 지표가 있다. 이 수치로 팔로우 수를 추정하지 않는다.
- 계정 시간대와 주간 게시 시간 설정도 조회할 수 있다. 현재 채널 시간대는 Asia/Seoul이다.
- 기존 비공개 CSV는 2026-05-29~2026-10-14의 139일이다. 일별 팔로우는 138일이며 나머지 1일은 결측이다. 이 파일의 존재는 Firestore에 가져오기 완료됐다는 의미가 아니다.
- 로컬 Buffer 읽기 키는 준비됐다. 현재 LLM 설정은 Anthropic이며 **OpenAI 키는 없다**. 새 성장 채팅의 실제 GPT 검증과 운영 반영은 OpenAI 키 설정 이후에 가능하다.

Buffer 성과 API는 실험적이고 개인 키를 통한 개인 사용 범위다. 지표가 누락되거나 바뀔 수 있고 일 단위 갱신으로 지연될 수 있다. 마지막 성공 동기화와 지표 갱신 시각을 함께 표시한다.

## 3. 화면과 사용 흐름

주요 메뉴는 세 개다.

1. **다음 게시:** 기본 진입 화면. 일별 팔로우 추이·자료 기간·유효 개수를 보여주고, 게시 형식(카드형/릴스)과 주제를 입력한다. 다음 7일 중 가능한 날짜·시간을 선택해 성장 상담을 요청한다. 답변 옆에 근거 게시물, 후보 시간, 표본 수, 자료 부족 이유를 표시한다. 질문·답변·로딩이 한 화면에 보인다.
2. **지난 게시:** Buffer 게시물 목록·필터·원본 링크·성과·지표 유무를 보여준다. 추천 당시의 계획과 실제 게시물을 연결하고 실험 결과를 확인한다. 사용자가 주제 태그·메모와 수동 보완 성과를 입력할 수 있다. 플랫폼 원본 수치와 수동 입력은 분리해 표시한다.
3. **내 데이터:** 일별 데이터 추가·조회·수정·삭제, 기간 선택 요약, CSV 가져오기·내보내기, 동기화 상태를 제공한다. 대화 기록은 이 화면의 명시적인 탭에서 목록·불러오기·삭제를 제공한다.

공통 상단에는 계정, 최근 동기화, 새로 불러오기 버튼이 있다. 로그인 전에는 기능 설명과 Google 로그인만 표시하고 실제 비공개 데이터를 노출하지 않는다. 모바일에서는 주요 메뉴를 짧은 탭으로 표시하며 표의 가로 스크롤을 핵심 작업에 강요하지 않는다.

기존 카드 제작·원고함·이미지 검토·라이브러리는 기본 메뉴에서 빼고 `기존 제작 도구`의 보조 진입으로 옮긴다. 기존 저장 자료와 API는 삭제하지 않는다. 새 첫 화면을 쓰는 데 이 도구들을 거칠 필요가 없다.

## 4. 수집과 저장

### 4.1 Buffer 수집

서버에서만 `BUFFER_API_KEY`를 사용한다. 고정된 `https://api.buffer.com`에 미리 정의한 읽기 GraphQL query만 보낸다. 임의 query, 외부 URL, 다른 채널 ID를 클라이언트가 지정하지 못하게 한다.

신규 서버 환경 변수는 `BUFFER_API_KEY`, `BUFFER_CHANNEL_ID`, `BUFFER_OWNER_UID`다. Firebase 인증과 기존 허용 UID 검사를 통과한 뒤 Buffer 소유 UID도 일치해야 한다. 한 서버의 개인 키를 다른 허용 사용자에게 공유하지 않는다. 계정에서 조회한 조직·채널 소속도 검증한다. 키는 프론트 설정·Firestore·로그·오류 응답에 넣지 않는다.

수집 항목은 조직·채널 식별자, 채널 시간대·연결 상태·게시 시간 설정, 게시물 ID·상태·캡션·형식·첨부물 메타데이터·태그·원본 링크, 실제/예약 게시 시각, 성과 배열과 갱신 시각이다. 댓글 내용·DM·팔로워 명단은 수집 범위에 없다. 미디어 파일 자체의 다운로드·자동 이미지 분석은 추가하지 않는다.

페이지를 끝까지 읽되 한 동기화는 최대 2,000개 게시물로 제한한다. 상한·커서 반복·HTTP/GraphQL 오류·필수 필드 불일치는 **부분 동기화 실패**이며 전체 완료로 표시하지 않는다. 알 수 없는 선택 지표는 원래 이름·타입·단위를 보존하고 분석에서 제외한다. API 요청은 제한 시간과 429 처리를 갖추며 자동 무한 재시도하지 않는다.

최초 수집 이후에는 사용자가 새로 불러오기를 눌러 갱신한다. 최근 60분 내 성공한 자료는 캐시를 사용하고 서버 측 사용자별 하루 5회 제한을 둔다. 키 만료·권한 오류이면 기존 자료와 마지막 성공 시각을 유지하고 재설정을 안내한다. 예약 자동화와 자동 게시·일정 수정은 만들지 않는다.

### 4.2 Firestore 구조와 일관성

- `data`: 기존 계정 일별 시계열. `date, metric, value, memo, owner_uid`를 유지한다.
- `conversations`와 메시지 하위 컬렉션, `requests`, `quotas`: 기존 대화·자동 저장·중복 방지·일일 AI 한도를 재사용한다.
- `buffer_connections`: 소유 UID, 채널 정보, 마지막 성공한 동기화 ID, 최근 시도 상태와 오류 코드. 비밀 키는 저장하지 않는다.
- `buffer_syncs`: 요청 UUID, 상태, 시작/완료 시각, 개수, 전체 페이지 완료 여부. `posts` 하위 컬렉션에 해당 수집 시점의 게시물과 성과를 불변으로 보관한다.
- `post_annotations`: 소유 UID+Buffer 게시물 ID에 연결한 주제 태그·메모·수동 보완 지표와 입력 시각·출처. 동기화가 덮어쓰지 않는다.
- `growth_experiments`: 추천 당시 질문·선택한 후보·근거 ID·기준 수치·관측 방식·버전, 실제 연결 게시물 ID, 사용자 메모와 상태.

새 동기화는 별도 세대에 저장한다. 전체 페이지 검증과 저장이 끝난 뒤에만 트랜잭션으로 연결 문서의 성공 포인터를 바꾼다. 부분 저장·실패·동시 실행 시 이전 성공 세대가 화면의 기준으로 유지된다. 네트워크 요청 중 Firestore 트랜잭션을 열지 않는다. 사용자별 실행 잠금과 요청 UUID를 사용해 중복 실행을 막고, 응답 유실 시 동일 UUID의 결과를 조회한다.

동일 게시물의 중복은 Buffer ID로 제거한다. `metricsUpdatedAt`과 지표 값이 동일한 재조회는 새로운 성과 관측으로 세지 않는다. 새 동기화의 현재 세대에 없어진 게시물은 현재 목록에서 제외하되 과거 실험 근거와 수집 이력은 보존한다. 플랫폼에서 삭제됐다고 추측하지 않는다.

### 4.3 기존 시계열과 과제 데이터

139일 CSV는 사용자 인증 후 기존 파서로 검증해 가져온다. 현재 날짜+지표가 같은 레코드는 기존 값을 우선하고 건너뛴 개수를 보고한다. 숨겨서 덮어쓰거나 최초 화면 방문만으로 자동 가져오지 않는다. UI에 가져오기 전후 날짜 수·유효 관측·결측 수를 표시한다.

Buffer 게시물의 누적 성과를 게시 날짜별로 합친 값을 기존 계정 일별 조회·팔로우 데이터에 섞지 않는다. 두 데이터는 측정 대상과 의미가 다르다. 일별 팔로우를 특정 게시물에 나눠 배정하지 않는다.

## 5. 분석과 추천 규칙

### 5.1 성장 지표

주요 성과는 플랫폼이 게시물에 귀속한 팔로우 수와 `팔로우 / 도달 × 100`이다. 전환율은 팔로우가 알려져 있고 도달이 양수인 경우만 계산한다. 팔로우 0은 유효한 0이며 누락은 null이다. 수동 보완 값이 있으면 원본과 출처를 모두 표시하고, 기본 비교 집단에는 플랫폼 관측끼리만 사용한다.

같은 형식끼리 개수·유효 팔로우 개수·결측 수·팔로우 수와 전환율의 중앙값을 계산한다. 릴스·카드형·스토리를 합쳐 성장 순위를 만들지 않는다. 저장·공유·조회는 진단 보조 지표이며 팔로우의 대체 정답으로 쓰지 않는다. 현재 릴스의 성장 전환 분석은 `게시물별 팔로우 자료 없음` 상태가 정상이다.

### 5.2 시간·주제 비교

채널 시간대로 변환한 **실제 게시 시각**을 사용한다. 예약 시각을 실제 시각의 대용으로 쓰지 않는다. 시간대는 고정 3시간 구간으로 나눈다. 같은 형식·같은 관측 방식에서 유효 게시물 3개 이상, 서로 다른 게시 날짜 2일 이상인 구간이 최소 2개일 때만 시간 구간의 관측 비교를 제시한다. 이 기준은 작은 표본의 비교를 제한하는 제품 규칙이며 통계적 유의성이나 인과를 보증하지 않는다.

유효 표본이 적으면 단일 게시물 사례와 원문 링크만 제시한다. 주제 태그는 사용자 입력을 우선하고 미분류는 그대로 둔다. 주제 검색은 캡션·태그의 일치 근거를 제시하며 관련 사례가 없으면 없다고 표시한다. GPT가 캡션에 없는 내용·시각적 특징을 읽었다고 주장하지 않게 한다.

### 5.3 관측 시점

과거 게시물의 현재 누적값은 `누적 관측`이다. 게시 후 경과 일수를 함께 보여주며 같은 노출 기간의 성과라고 표현하지 않는다. 초기 누적 관측으로 계산한 패턴은 탐색 근거로만 사용하고 시간 효과의 입증이나 기대 팔로우 증가량을 제시하지 않는다.

앞으로는 저장된 관측 중 `metricsUpdatedAt - sentAt`이 6~8일인 관측을 `7일차 부근 관측`으로 구분한다. 소스 갱신 시각·서버 수집 시각·관측 지연을 함께 보관한다. 이 관측이 실제로 저장된 게시물끼리만 같은 기간 비교에 쓴다. 과거 7일차 값을 현재 누적값에서 복원하지 않는다. 수동 동기화로 이 구간을 놓치면 `비교 시점 자료 없음`으로 남긴다.

### 5.4 추천 결과

사용자가 선택한 가능한 시간과 다음 7일의 채널 게시 시간 설정을 바탕으로 후보를 만든다. 기존 설정은 사용자의 가능한 시간으로 **미리 표시할 수 있지만 확인 없이 생활 일정으로 확정하지 않는다.** 후보가 2개 미만이면 가능한 수만 보여주고 추가 시간을 입력할 수 있게 한다.

분석에 근거한 후보는 비교 표본·관측 방식·기준 중앙값·근거 게시물 ID를 갖는다. 자료가 부족한 후보는 `새 실험`이며 기대 팔로우나 개선률을 붙이지 않는다. 시간만 바꾸는 실험에서는 같은 형식과 비슷한 주제를 유지하도록 제안한다. 한 게시물만으로 최적 시간이나 개선 효과를 확정하지 않는다.

모든 결과는 목표 `followers`, 자료 버전, 분석 기준일, 후보 배열, 근거 ID, 각 제외 이유, 부족한 자료를 구조화해 저장한다. 확률처럼 보이는 임의 신뢰도 점수는 만들지 않는다.

## 6. GPT 채팅과 실험 기록

성장 상담은 기존 `POST /api/chat`에 `mode="growth"`를 추가한다. 기존 chat/ideas/draft 요청과 저장 이력은 호환되게 유지한다. 성장 모드에서는 OpenAI 제공업체를 명시적으로 사용하고 키가 없으면 설정 필요 오류를 반환한다. Anthropic으로 조용히 대체하거나 모의 답변을 실제 GPT 답변으로 표시하지 않는다. 통계·후보·근거는 모델 호출 없이도 화면에서 볼 수 있다.

현재 대화 서비스의 예약·UUID·실패 복구·자동 저장을 재사용한다. 성장 모드에서는 일반 원고 검색 대신 현재 성공한 Buffer 세대와 계정 일별 요약을 바탕으로 컨텍스트를 준비한다. `/api/data/summary`와 같은 일별 요약 함수의 결과를 시스템 프롬프트에 주입하고, 성장 비교 통계·자료 부족 사유도 서버가 계산해 전달한다.

캡션·사용자 메모·과거 대화는 신뢰하지 않는 참고 자료로 별도 입력 역할에 둔다. 전체 51개 캡션을 매번 보내지 않고 선택 형식·주제에 맞는 최대 5개, 각 캡션 최대 2,000자만 전달한다. GPT는 추천의 설명과 실행할 실험 한 가지를 작성한다. 시간 후보·수치·실험 점수 계산은 Python이 담당한다.

기존 응답 구조에 선택적 `growth` 필드를 추가한다. 이 필드의 후보와 수치는 서버 계산 결과를 그대로 붙이고, 모델이 새 수치를 만들거나 후보를 변경하지 못하게 한다. 모델이 반환한 근거 ID는 실제 제공한 소유 게시물 ID 집합으로 검증한다. 결과를 assistant 메시지에 저장해 불러왔을 때 당시 근거와 버전을 재표시한다. 이전 대화를 불러올 때 최신 수치로 과거 답변을 바꾸지 않는다.

`이 시간으로 실험 저장`은 GPT를 다시 호출하지 않는다. 저장된 추천 결과와 후보 ID를 서버에서 조회해 기준과 함께 복사한다. 사용자가 게시 후 Buffer 게시물을 직접 선택해 연결하며 서버는 소유권·형식·게시 완료 여부를 확인한다. 추천 시간과 실제 시각의 차이를 보여주고, 60분 이상 차이 나면 `계획과 다른 시간`으로 기록한다. 이 차이를 숨기고 추천 성공으로 세지 않는다.

실험 상태는 `planned`, `linked`, `awaiting_observation`, `observed`, `cancelled`다. GPT 생성과 Buffer 게시 예약은 연결하지 않는다. 비교 가능한 관측이 없는 경우에도 연결 사실과 누적 성과를 볼 수 있지만 효과 판정은 보류한다. 실험과 동기간의 계정 일별 팔로우 변화는 별도 참고 정보이며 해당 게시물의 기여량으로 표시하지 않는다.

## 7. API와 코드 경계

과제 필수 데이터 CRUD·요약·대화 저장/목록/상세/삭제·채팅 API는 모두 유지한다. 신규 API는 다음으로 제한한다.

- `GET /api/buffer/status`: 소유 계정·연결·동기화 상태, 성공한 자료의 기간·형식별 개수·지표 보유 현황. 비밀 값 제외.
- `POST /api/buffer/sync`: 클라이언트 요청 UUID로 동기화 시작. 동시 실행·쿨다운을 검사한다.
- `GET /api/buffer/sync/{request_id}`: 응답 지연·유실 시 상태와 성공 결과 확인.
- `GET /api/buffer/posts`: 현재 성공 세대의 게시물 목록. 형식·상태·기간 필터, 고정 정렬, 최대 50개 단위 페이지.
- `PUT /api/buffer/posts/{id}/annotation`: 로컬 태그·메모·수동 보완 값만 수정한다. Buffer 원본은 변경하지 않는다.
- `GET /api/growth/summary`: 형식별 성장 지표·누락·시간 구간 비교·자료 제한을 계산한다.
- `POST/GET /api/growth/experiments`: 저장된 후보로 실험 생성 / 목록 조회.
- `PUT /api/growth/experiments/{id}`: 소유 게시물 연결·메모·취소를 검증해 반영한다.
- `POST /api/data/import`: 139일 CSV 등 동일 계약의 시계열 가져오기. 2MB·최대 366일, 기존 파서와 중복 건너뛰기 규칙 사용.

`buffer_client.py`는 고정 읽기 쿼리·전송·응답 검증, `buffer_service.py`는 인증 소유권·동기화 세대·저장, `growth_analytics.py`는 순수 통계·후보와 결측 사유, `growth_service.py`는 실험 상태와 근거 보존을 맡는다. 라우터는 인증·Pydantic 검증 후 서비스를 호출한다. 기존 `chat_service.py`의 컨텍스트 준비 분기에 성장 모드를 추가하고 공통 저장 절차는 유지한다.

프론트는 `growth.js`와 `growth.css`에 새 주 화면을 두고 기존 인증·API·알림을 재사용한다. `app.js`, `index.html`의 기본 진입과 메뉴를 수정하고 빌드 복사·해시 대상도 함께 바꾼다. 새 프레임워크·차트 라이브러리·에이전트 런타임은 설치하지 않는다.

## 8. 오류와 보안

- 401/403은 기존 Google 로그인·등록 UID 검사와 Buffer 소유 UID 검사를 구분해 안내한다. 설정 변경만으로 타 사용자 계정에 접근할 수 없어야 한다.
- Buffer 401/403, 429, 타임아웃, GraphQL errors, 빈 결과, 부분 응답, 페이징 실패를 각각 상태 코드로 저장하되 키·헤더·원문 응답은 공개 로그에 남기지 않는다.
- 원격 수치와 사용자 입력은 유한한 비음수 값·허용 단위·시간 형식·문자 길이로 검증한다. 비율과 정수 지표를 구분하며 null을 0으로 바꾸지 않는다.
- 원본 링크·썸네일은 HTTPS URL만 허용하고 화면 문구는 textContent로 렌더링한다. 소유권을 검사하지 않은 원격 ID를 근거 링크나 실험에 연결하지 않는다.
- 새 동기화 실패·모델 실패·응답 유실 시 입력과 마지막 성공 자료를 유지한다. 미완료 상태를 성공 또는 0건으로 바꾸지 않는다.
- 모바일·로그아웃·계정 전환 시 이전 UID의 화면 데이터와 진행 상태를 비운다. 개인 지표를 익명 사용자에게 샘플로 보여주지 않는다.
- 실제 개인 데이터·키·성과 화면은 공개 코드/PR/README에 넣지 않는다. 제출 예시는 합성 데이터임을 표시하고, 실제 자료 공개는 별도 승인 범위다.

## 9. 검증과 제출

구현 검증은 다음의 의미 있는 경계에 집중한다.

1. Buffer 다중 페이지·완료 커서·중복·단위·누락·401/429/타임아웃/부분 오류와 소유권. 부분 저장 후 성공 포인터가 바뀌지 않는지 검증한다.
2. 팔로우 0/null, 도달 0, 형식 분리, 같은 관측 시점, 시간대 경계, 표본 미달, 릴스 팔로우 결측, 미래 시각과 미게시 상태 제외를 테스트한다.
3. 성장 채팅에 실제 계산된 요약과 제공한 근거만 들어가는지, GPT 없는 상태의 오류·UUID 중복·저장 결과 복구·이전 대화 호환을 검증한다.
4. 실험 저장·타 UID 연결 거부·실제 게시 시각 차이·7일차 관측 누락을 검증한다.
5. 브라우저에서 로그인 이후 동기화 → 질문/답변/요약 → 실험 저장/연결 → 대화 불러오기 → 데이터 CRUD를 검증한다. 빈 자료·오류·모바일도 포함한다.
6. 기존 Python·정적 빌드·필수 CRUD/대화 회귀 검증을 실행한다. 기존 보조 도구는 보관 경로 진입과 저장 자료 접근이 유지되는지 확인한다.

실제 Buffer 확인은 키를 노출하지 않는 읽기 조회로 한다. Firestore 쓰기와 실제 OpenAI 호출, 두 플랫폼 배포는 각각 수행 사실과 결과를 분리해 기록한다. 현재 OpenAI 키 부재를 코드상 설정 여부만으로 해결됐다고 보고하지 않는다.

README는 새 서비스의 목적·사용 흐름·기술·현재 구현/배포 상태·환경 변수·로컬 실행·API·실험적 지표 제한·데이터 출처·제출 화면으로 다시 작성한다. 제출 화면에는 요약과 질문/답변, 데이터 CRUD, 대화 불러오기를 반드시 포함한다. 합성 자료와 실제 연동 검증을 구분한다.

최종 승인 후 구현 계획을 작성한다. 구현 완료는 실제 기능 검증으로 판단하며 main 병합·운영 배포·실제 개인 데이터 공개를 자동으로 완료 처리하지 않는다.
