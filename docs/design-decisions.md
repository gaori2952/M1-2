# 설계 선택과 구현 흐름

[README로 돌아가기](../README.md)

## 사용 흐름

1. [서비스](https://m1-2-frontend-theta.vercel.app/)와 [Swagger](https://m1-2-6ae7.onrender.com/docs)에 접속합니다.
2. Google 로그인 후 `내 데이터 → 직접 기록`에서 날짜·지표·값·메모를 추가합니다. Firestore 저장과 목록 반영을 확인합니다.
3. 값을 수정·삭제하고 `/api/data/summary`의 평균·최대값을 확인합니다. 같은 기간의 수치를 채팅으로 질문해 요약 반영 여부를 확인합니다.
4. `대화 기록 → 불러오기`로 질문·답변·근거를 복원합니다. 새로고침 후에도 유지되는지 확인합니다.
5. 작은 화면에서 메뉴·채팅·이미지 첨부·데이터 입력·대화 불러오기를 확인합니다.

데이터 API: `POST/GET /api/data`, `PUT/DELETE /api/data/{id}`, `GET /api/data/summary`.

대화 API: `POST/GET /api/conversations`, `GET/DELETE /api/conversations/{id}`. 목록에는 전체 메시지가 없고 상세 조회에 `messages`가 포함됩니다.

채팅 API: `POST /api/chat`. 요청 상태는 `GET /api/chat/requests/{request_id}`로 조회합니다.

## 역할과 저장 구조

### 라우터 · 서비스 · 계산 · 저장소

- `routes/`: URL, 요청 스키마, 인증, HTTP 응답을 연결합니다.
- 서비스: 채팅 생성·자동 저장·게시물 수집 등 업무 흐름을 처리합니다.
- `analytics.py`: 외부 연결 없이 통계만 계산합니다. API와 채팅이 같은 함수를 재사용합니다.
- `store.py`: Firestore 읽기·쓰기·트랜잭션·캐시를 담당합니다.

계산 기준 변경이나 저장소 문제를 다른 역할과 분리해 수정·검사하기 위한 구성입니다.

### Firestore 컬렉션

```text
data/{id}                    날짜·지표·값·메모·출처·owner_uid
conversations/{id}           제목·메시지 수·갱신 시각·owner_uid
  └ messages/{id}            순서·역할·본문·작업 결과·근거
requests/{id}                요청 처리 상태·저장된 응답
buffer_syncs/{id}/posts/{id}  수집 시점의 게시물·성과
post_readings/{id}           이미지 판독문·요약·출처 서명
```

`data`는 사용자·날짜·지표 조합으로 중복을 막고 기간별로 집계합니다. 대화는 목록용 정보와 개별 메시지를 나눠 목록 조회에서 전체 본문을 읽지 않게 합니다. 메시지 순서와 당시 근거도 저장해 불러온 답변의 맥락을 유지합니다.

### Pydantic 검증

API 진입 시 날짜·지표 종류·음수가 아닌 정수·메모 길이·기간 순서·이미지 개수와 형식을 검사합니다. 알 수 없는 필드는 거부합니다. AI 출력도 응답 스키마와 실제 참고 ID를 검증한 후 저장합니다.

### 프론트 상태 흐름

- 데이터: `입력 → 저장 → 목록·요약 재조회`.
- 채팅: `입력 → 로딩 → 응답 저장 → 메시지 표시`.
- 불러오기: `대화 목록 → 상세 조회 → 메시지·근거 복원`.
- 연결 실패: 입력과 요청 ID를 유지하고 처리 상태를 조회합니다.

## 데이터와 AI 연결

### 컨텍스트 주입

`/api/data/summary`와 채팅이 같은 `summarize()`를 사용합니다. 기간·평균·최대·최소·전기 대비 추세를 계산해 시스템 프롬프트의 `[사용자 데이터 요약]`에 넣습니다. 캡션·판독문·과거 대화는 별도의 참고 입력으로 전달합니다.

사용자가 데이터를 반복 설명할 필요를 줄이고 계산 기준을 일정하게 유지할 수 있습니다. 다만 요약 과정에서 세부 내용이 빠질 수 있고, 요약만으로 인과관계나 미래 성과를 알 수는 없습니다.

### 요약 API 분리

화면과 AI가 같은 계산 결과를 재사용합니다. 기본은 **저장된 최신 날짜까지 7일**과 직전 7일을 비교합니다. `start`, `end`로 기간을 지정할 수 있습니다.

### 대화 자동 저장

AI 응답 검증 후 질문·답변·근거와 대화 정보를 한 트랜잭션으로 저장합니다. 일부만 저장되는 상황을 줄이고, 같은 요청 ID의 재시도에는 기존 결과를 반환합니다. 이전 작업 원문도 후속 질문에 전달합니다.

### 환경 변수

비밀 키를 소스에서 분리하고 로컬·운영 설정을 각각 적용합니다. 서버는 `.env` 또는 Render 환경 변수, 프론트는 Vercel 빌드 환경 변수를 사용합니다. 프론트에는 API 주소와 공개 Firebase 설정만 포함합니다.

## 운영과 확장

### 콜드스타트

첫 요청이 길어지면 서버 시작 안내를 표시합니다. 입력을 보존하고 요청 ID로 완료 여부를 확인해 중복 생성을 줄입니다.

### CORS

Vercel과 Render의 출처가 달라 브라우저가 API 응답을 제한합니다. FastAPI에 정확한 허용 origin·메서드·헤더를 설정하고 오류 응답에도 적용합니다. Firebase Authorized domains는 로그인 허용 설정으로 별도 관리합니다.

### 악성 입력과 데이터 오염

보호된 API에서 Firebase 토큰과 소유 UID를 확인합니다. Firestore의 브라우저 직접 접근은 차단하며, Admin SDK를 쓰는 서버에서도 소유권을 검사합니다. Pydantic으로 입력을 검증하고 가져온 원본은 수정할 수 없게 분리합니다.

참고 글의 명령을 시스템 지시로 취급하지 않고, 화면 출력은 HTML로 실행하지 않습니다. 이미지의 실제 형식·해시·크기와 서버 다운로드 주소도 검사합니다.

### 데이터 증가와 요약 기준 변경

- **최근 30일로 변경:** `backend/app/analytics.py`의 기본 기간을 30일로 바꾸고 기간 관련 검사를 갱신합니다.
- **데이터 규모 증가:** 현재는 사용자별 최대 10,000개를 조회한 뒤 집계합니다. `store.py`에 인덱스·기간 조건·페이지네이션을 적용하고 서비스가 필요한 범위만 조회하도록 확장해야 합니다.
- **DB 한도 초과:** 원인을 안내하고 반복 읽기는 캐시로 줄입니다.
